# Project Brief — Crypto Market Monitor

更新：2026-11-12。現行要件。機能A〜Dと機能Eの追加ダッシュボードを実装・検証済み。Eのユーザーレビュー、ST/UAT、デプロイは未完了。

## 目的・利用者・公開

公開市場データから価格と取得状況を確認し、将来は複数市場・複数通貨ペアの裁定候補をコストとともに評価する。主な利用者は1名。第三者が公開環境の動作を確認できる状態を目指す。ローカル動作やGitHubへの掲載だけで公開完了とはしない。

本番構成・デプロイ先は未確定。機能E後のGit/CI・基本結合を進め、本番相当環境の構築と本格STの前に、PaaS/小規模VM等を継続収集・MySQL永続化・費用・保守負担で比較する。過去のOCI/Nginx案を採用済みと扱わない。

## Phase 1の機能要件【合意済み】

1. Coinbase Exchange / BTC-USD / Level 1のBid・Askと各数量を取得し、共通形式へ変換・検証する。
2. MySQLに観測と実行履歴を保存する。同じ価格も毎回保存する。
3. 1実行は1市場・1通貨ペア。成功・失敗・スキップ・中断を区別する。
4. RUNNINGで開始し、再起動時に残っているRUNNINGをINTERRUPTEDへ整理してから定期収集を開始する。単一バックエンド前提。
5. オークション中は価格を保存せずSKIPPEDとする。
6. 回収コミット後に初回即時、以後は前回終了から60秒のfixed delayで直列収集する。即時再試行はしない。
7. 市場一覧→選択市場詳細（24時間のMid/スプレッド推移・期間内全観測のスプレッド統計）→収集状況の順で表示する。現在の対応はCoinbase Exchange / BTC-USDの1市場。履歴は最新100件を取得し初期折りたたみ、開くと5件、詳細展開後は10件ページ送り。ログイン画面なし。
8. 画面の初回・手動・30秒更新は3参照APIを並行取得し、外部収集を起動しない。部分失敗時は前回値を保持。鮮度は1秒の表示時計で進め、3分以上を注意とする。
9. REST API、エラー処理、テスト、README、GitHub、公開環境での動作確認を整える。

## 非機能・運用要件

- 数値はBigDecimalとDECIMALで精度を維持。APIの価格・数量とIDは文字列。
- DB保存・API時刻はUTC、画面はJST明記。observed_atとsource_atを区別する。
- 外部通信のタイムアウト・429・異常データを処理し、外部通信中にDBトランザクションを保持しない。
- 自動テストは外部取引所の実通信に依存させない。
- 秘密情報は外部設定。SQL・内部例外を公開応答へ出さない。
- DBと管理機能の公開を制限する。画面用参照APIは必要な範囲で公開する。
- 費用は無料優先。課金・常時Bot運用は用途と費用を説明して別途判断する。
- 非利用時の停止を許容し、全履歴の永久保持や24時間連続収集は必須としない。
- 停止による未観測期間を明示。バックアップ・復旧水準は保存する情報の重要性に合わせる。
- ローカルでのMySQL永続保存方針は維持。保存期間と削除条件は別途合意する。100件は表示件数であり保存上限ではない。
- 履歴の永久保存が不要でも、動作中の参照・制約・トランザクションは不要にならない。DB方式を無断で変更しない。

## フェーズの境界

Phase 1は収集・保存・参照・公開の土台。Phase 2で複数取引所／ペア、WebSocket、鮮度・時刻差、数量・手数料等の計算、候補表示へ拡張。Phase 3で仮想取引・残高・損益と同時更新を扱う。

実取引・資金移動・秘密鍵・認証付き注文APIは現スコープに含まない。将来のBotという意向を、自動売買実装の承認とは扱わない。

## Phase 1の完了条件

- 取得→検証→DB保存→参照API→画面がローカルで再現できる。
- 異常応答、失敗、スキップ、中断復旧、保存の整合性をテストできる。
- 公開方式を確定し、公開URLから利用可能な構成を実装・確認する。
- 休止・初回待ち・履歴保持・鮮度の制限と、再起動・停止手順を説明する。
- README・構成図・DB設計・API契約・デモ手順が実装と一致する。
- Render代替を使う場合はDB方式・機能制限・受け入れ条件の変更を明示的に合意する。
