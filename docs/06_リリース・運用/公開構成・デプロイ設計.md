## 2. サーバーという言葉と今回の役割

Webサーバー、アプリサーバー、DBサーバーは役割を指し、3台のPCや3台のVMを必須にしない。同じVM上で別プロセスや別コンテナとして動かせる。

| 要素 | 役割 | 開発・公開での違い |
|---|---|---|
| Vue | ブラウザで画面を動かす | 公開時はビルド済みHTML/JS/CSSを配布 |
| Vite | 開発サーバーとビルド | 公開環境で開発サーバーやpreviewを運用しない |
| Nginx | 静的配信、リバースプロキシ | 自前VM案で入口・配信・API転送を担当 |
| Spring Boot | REST API、収集、検証、保存、将来の計算 | JVMプロセスを起動し続ける必要がある |
| 組込みTomcat | Spring MVCのHTTP受信・Servlet実行 | Bootの起動に含める。別Tomcatを追加する必要はない |
| MySQL | データと制約・トランザクション | DBプロセスと、必要なら永続ストレージを用意 |

HTTPサーバーはHTTPで要求・応答するソフトウェア。Webサーバーは概ね同義に使われるが、静的配信だけに限定されない。アプリサーバーは業務ロジックの実行環境を指し、HTTP受信の役割と重なる。

静的ホスティングは配信基盤をサービス側が管理する。Nginxはその配信等を自分で設定・運用するソフトウェア。静的ホスティングだけではSpring BootやMySQLを動かせない。

以前のApache/Tomcat/webpackとの対応：webpackとViteはどちらもフロントのビルド・開発支援。Viteを単なるwebpackの上位互換とは扱わない。Vueの本番成果物は静的配信し、APIはBootへ転送する構成が可能。

根拠：[Viteの静的デプロイ](https://vite.dev/guide/static-deploy.html)、[Nginx公式ガイド](https://nginx.org/en/docs/beginners_guide.html)。Spring Bootの依存・組込みTomcatは採用する3.5系公式資料で環境構築時に再確認する。

## 3. ローカルと公開の構成

### ローカル【既存方針】

ブラウザ → Vite開発サーバー → /api転送 → Spring Boot → Docker ComposeのMySQL。
バックエンド → Coinbase。DB接続・外部通信・収集はフロントに実装しない。

### OCI Always Free Linux VM【選定方針・未確保】

```text
インターネット
  ↓ HTTPS
OCI Always Free Linux VM
  Nginx ── Vueのdistを配信
    └ /api → Spring Boot（組込みTomcat）→ MySQL
                    └ Coinbaseへ通信
```

- まず単一バックエンド。複数台化は未対応。RUNNING回収の単一実行前提を維持する。
- 公開用Docker ComposeでNginx・Boot・MySQLを構成する方針。ローカルのDBだけComposeという方針は維持し、公開用設定を分ける。
- Nginxで同一オリジンの画面とAPIを提供する方針。基本の公開入口はHTTPS 443。Boot 8080/MySQL 3306は内部に限定し、管理経路は別に設計する。
- MySQLのデータはvolumeへ配置。volumeはバックアップではなく、VM喪失にも耐えるとは限らない。
- JVM・MySQL・OS・コンテナの合計メモリ、CPUアーキテクチャと各イメージ対応、ディスク、再起動動作を確認する。
- 無料枠の提供条件、リージョンの空き、停止・回収条件、外向き通信、帯域・ストレージ・IP等の課金を確認する。無料で確保できると保証しない。
- 証明書・ドメイン・OS更新・ログローテーション・バックアップは自分で運用する範囲になる。

### 自宅Windows/WSL2とクラウドVMの違い

自宅PCでも開発・ローカル構成検証は可能。ただし公開時はPCの電源、回線、NAT、外部到達性、証明書、自宅ネットワークの分離を自分で扱う。WSL2導入は公開基盤ができたことを意味しない。
クラウドVMは手元PCから独立して起動できるが、OS・ネットワーク・更新・費用管理は残る。EC2はこの種の選択肢の一例であり、今回採用決定したサービスではない。
開発PCではDocker Desktop/WSL2の導入・Compose DB起動を確認済み。将来の負荷に対する割当て・使用量は別途検証する。PC性能と外部公開の可用性は別問題。

## 4. Render Freeへの代替

2026-10-27に公式資料を確認。提供条件はデプロイ直前に再確認する。

- Free Web Serviceは無通信時に休止し、再開待ちがある。アプリから取引所へ行う通信だけを根拠に常時稼働できるとは扱わない。
- ローカルファイルは再起動等で失われ、Freeには永続ディスクを付けられない。
- Render公式のMySQL構成はprivate serviceとdiskを使う。これを無料構成と見なさない。
- Free Postgresにも保持期限があり、永続MySQLの無変更代替にはならない。
- 無料枠の稼働時間・転送・ビルド・外向き通信等の制限がある。

根拠：[Render Free](https://render.com/docs/free)、[Render MySQL](https://render.com/docs/deploy-mysql)。

### 代替の比較【方式未確定】

| 案 | 維持できること | 変わること・確認点 |
|---|---|---|
| Render App + 外部MySQL | JPA・SQL・FlywayのMySQL方針 | DBサービスの無料条件、TLS、接続数、外向き通信、休止後の再接続 |
| Render App + 別DB製品 | 論理モデルの多く | Driver、SQL、Flyway、ID採番、型・制約の差。実DBでの試験が必要。無断変更しない |
| Render＋H2等の一時DB＋サンプルデータ（未採用案） | 公開画面・APIの一部 | 再起動で履歴消失。MySQLとSQL/Flyway/ロック/Txが異なり得る。サンプルとライブデータを区別し、正規MySQLのテストを維持。通常版と同等扱いしない |

無料VMが確保できない場合、まずMySQLを維持できる外部DBの条件を調べる。適切な無料DBがない場合は、少額課金と機能を制限した公開版を比較してユーザーが決める。

MySQL・Boot・Nginxの複数プロセスをFreeの1サービスへ詰めれば解決する、とはしない。DBの寿命・メモリ・起動順・障害復旧が別問題になる。

### 移植性を確保する設計提案

Boot用Dockerfileを用意してJavaアプリの配布形式を共通化する。接続先・パスワード・HTTPポート・ログ・収集有効/無効・間隔・鮮度設定を環境変数／Spring Profilesから与える。収集実処理はSchedulerからServiceへ分離する。ドメイン・VMのIP・特定の絶対パスを業務コードへ埋め込まない。
Vueの成果物はNginx/静的ホスティング/Boot配信のいずれにも配置できる形にする。APIの契約と収集ロジックは配信先に依存させない。
Renderで静的サイトとAppを別オリジンにするならAPI接続先とCORSを明示的に設定。別案としてBootから同一オリジンで静的配信する構成を比較する。配信案は未決定。
設定分離だけでDB製品・休止・履歴消失の差を吸収できると説明しない。専用プロファイルや新しい永続化抽象層は必要性を確認して最小限にする。

## 5. 停止許容・履歴保持・リアルタイムの意味

全履歴の永久保存が不要という意向は、Phase 1の保存・履歴機能の撤回ではない。保持期間・削除方法・候補の根拠を残す範囲を別途決める。

非利用時停止を許容しても、停止中の裁定機会は検知できない。再開直後は最新観測が揃うまで「準備中／判断不可」とする設計を検討する。空白期間を過去価格の補間で観測済み扱いにしない。

「デモ閲覧」は第三者が公開URLを開いて動作を見ること。「自分がその場で監視する運用」「無人の24時間Bot運用」は別の稼働条件。前2つでよい現状から、無人運用の可用性を保証しない。

Phase 2では以下を別々に設計する。

1. 取引所 → バックエンド：WebSocketで価格・板を受信する方針。市場別仕様、再接続、購読・解除、欠損・順序、板の再同期を検討。
2. バックエンド → 画面：WebSocket/SSE/ポーリング等を比較して決定。取引所側WebSocket採用で自動的に決まらない。
3. 計算・保存：最新状態と全イベント履歴を分ける。高頻度受信をそのまま全件DB保存するかは保持要件から決める。
4. 復旧：再接続しただけで鮮度を回復したと見なさず、比較可能な観測が揃ってから候補計算を再開する。

RenderはWebSocketに対応するが、切断・休止・再配置の可能性を前提に再接続する。[Render WebSocket](https://render.com/docs/websocket)。サポートの有無はBotの連続稼働保証とは異なる。

## 6. 公開時の境界・最低限の運用【詳細は要合意】

- 公開入口はHTTPS。DBと管理ポートは内部ネットワーク。SSH等の管理アクセスは限定する。
- 画面用GET APIは公開画面から必要。/apiという名前だけで内部専用にならず、CORSだけでアクセス制御できるわけでもない。
- 実行履歴を一般公開する範囲・説明文・レート制限を確認し、内部例外・ホスト名・資格情報を出さない。
- 収集起動、設定変更、DB管理、Actuator等は公開しないか、必要性を確認して別の制限を設ける。ログイン画面なしは管理APIを無保護にする意味ではない。
- DB接続はアプリ専用ユーザー。秘密は環境変数等で管理し、フロント成果物・Git・ログに入れない。
- 起動順はDB/Flyway→RUNNINGの回収→収集開始。単一インスタンスの停止・再起動で検証する。
- 最小のヘルス確認・実行ID付きログ・ログ容量制限・停止と復旧手順を用意する。
- 保存対象が再取得可能な観測だけか、将来の仮想残高・設定も含むかでバックアップ水準を変える。volumeだけで保護完了にしない。
- OS/JDK/ライブラリ、特にBoot 3.5.16の公開時サポート・脆弱性を再評価する。
- 予算上限・請求通知・無料枠超過時の停止方法を決める。課金を伴う契約・構築は事前に判断する。

## 8. OCIの早期確認とRender切替の判断手順

引き継ぎ資料で、事業者はOCI Always Free、Nginx＋Boot＋永続MySQLを同一Linux VMのComposeで運用する選定方針まで補完できた。具体的なshape・OS版・CPU/メモリ・無料枠確保は未検証。

2026-10-27に[OCI公式Always Free資料](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)を確認。対象リージョンでの容量不足と、低利用インスタンスの回収条件がある。古い無料枠のCPU/RAM数値をそのまま採用せず、確保時のコンソールと公式条件で再確認する。

順序：

1. API基本設計を合意し、正規MySQL構成の環境準備を進める。
2. 公開実装を本格化する前に、OCIアカウント/無料枠・容量・利用条件・必要リソースを調査する。契約や課金操作は別途扱う。
3. 確保可能なら正規のNginx/Boot/MySQL構成を構築・検証する。ARM系shapeならJDK/MySQL/Nginxのイメージとビルドの対応を確認する。
4. 確保不可・難航なら、無料優先の意向からRender Freeを検討する。いつ難航と判断するかは作業状況を共有して決め、無期限に再試行しない。
5. 外部永続MySQLを用意できるかを検証する。不可なら、H2等の一時DB＋サンプルの公開デモと少額VMを比較し、制限を説明して採用を決める。
6. 代替の実証は本体の初期実装と分離する。正規MySQLのFlyway・制約・トランザクションのテストを維持する。

H2デモを使う場合の追加設計：デモモード表示、サンプルと実観測の区別、サンプルの時刻、古いデータを最新扱いしないこと、再起動時の初期化、保持期間、マイグレーション差分。H2互換モードでもMySQL同等の証明にはならない。
起動時収集や明示的トリガーは、この切替で自動採用しない。参照GETはDB読取りのみという既存契約を維持する。
