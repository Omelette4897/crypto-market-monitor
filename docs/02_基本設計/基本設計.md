# Phase 1 基本設計

更新：2026-11-12。合意済みの基本設計。機能A〜DとEの追加ダッシュボードは実装・検証済み、公開は未実施。現行の詳細は機能別設計を参照する。

## 1. システム構成

合意済み：Vue 3 / TypeScript / Tailwind CSS / Vite、Java 21 / Spring Boot 3.5.16 / Maven / Spring MVC / JPA / Flyway / MySQL。Nuxtは使わない。

画面の参照と外部収集は分離する。ブラウザはバックエンドAPIからDBの保存データを読み、Coinbaseを直接呼ばない。Coinbase収集はバックエンドで行う。

```text
ブラウザ（Vue）→ REST Controller → 参照Service → Repository → MySQL
Scheduler → 収集Service → CoinbaseClient → Coinbase API
                       → 検証・保存 → MySQL
```

同一リポジトリのfrontend/backend/docs配置と開発時の/apiプロキシを採用済み。公開構成は未確定。本番相当環境構築/本格ST前に候補を比較する。開発時はDBだけCompose。

## 2. 画面・操作【合意済み】

市場モニター1ページ。Coinbase Exchange / BTC-USDを初期対象とする。

```text
ヘッダー：アプリ目的・対応市場数・画面データ最終取得・更新操作
市場一覧：対応する取引所/ペア・Mid・Spread/率・鮮度（現在1市場）
選択市場詳細：Mid・Bid/Ask・数量・Spread/率・観測時刻
  24時間分析：Mid/Spreadチャート・期間内全観測のスプレッド平均/最大/最小
収集実行履歴：稼働サマリー（直近結果・処理時間・成功率・鮮度/警告）を内包
  履歴明細は初期折りたたみ→開くと5件→詳細10件ページ送り
```

初回・手動・30秒周期でDB参照3 APIを取得し、Coinbase収集は起動しない。読込/空/エラーは領域別に扱い、部分失敗時は前回値/成功日時を保持する。ヘッダーは3 APIの全成功時刻を表示する。

金額は十進精度を保ち、率だけ6桁へ丸める。鮮度は端末時計で1秒ごとに進め、観測から3分以上を注意とする。古い保存値を取引可能な現在価格とは表示しない。MidはVueで計算し、スプレッド系列と24時間統計はサーバーで算出する。詳細は[機能E設計](../03_詳細設計/Phase1_Vue業務画面_詳細設計.md)第9〜11節。現行の情報配置は第11節を正とする。

## 3. DBの業務上の意味【2テーブル案を合意】

1行の意味から分割する。collection_runsは「1市場・1通貨ペアの収集実行1回」、market_snapshotsは「その実行で検証を通過した価格観測1件」。
失敗・スキップでは実行履歴だけが存在する。1実行→観測0件または1件。同価格でも別実行なら新しい観測を保存する。

1テーブルで状態と任意の価格一式を保持する設計も成立する。分割の選択理由は、収集状況の管理と分析に使う観測を区別し、観測項目を必須にできること。分割だけで全整合性が保証されるわけではない。
取引所・通貨ペア別の一覧は同じ事実の検索結果であり、画面の一覧ごとにテーブルを作らない。マスターは独立した管理属性が必要になる段階で検討する。

### collection_runs

| 項目 | 必須 | 意味 |
|---|---|---|
| id | はい | BIGINT、PRIMARY KEY、AUTO_INCREMENT |
| exchange | はい | 対象市場。初期COINBASE_EXCHANGE |
| symbol | はい | 統一通貨ペア。初期BTC-USD |
| status | はい | RUNNING/SUCCESS/FAILED/SKIPPED/INTERRUPTED |
| started_at | はい | 開始時刻、UTC |
| finished_at | いいえ | 終了結果を確定した時刻。RUNNING/INTERRUPTEDはnull |
| interruption_detected_at | いいえ | 起動時に中断を検出した時刻。INTERRUPTEDのみ設定 |
| result_code | いいえ | 失敗・スキップ・中断理由の分類。成功時null |

result_messageは保存しない。APIでresult_codeから表示用説明を生成する。理由分類は価格取得・保存・参照APIの実装と個別詳細設計に対応する。詳細な調査情報は実行ID付きログへ。

### market_snapshots

| 項目 | 必須 | 意味 |
|---|---|---|
| id | はい | BIGINT、PRIMARY KEY、AUTO_INCREMENT |
| run_id | はい | collection_runsへの外部キー、UNIQUE |
| bid_price | はい | 最良買気配価格 |
| bid_size | はい | 買気配価格水準の合計数量 |
| ask_price | はい | 最良売気配価格 |
| ask_size | はい | 売気配価格水準の合計数量 |
| observed_at | はい | HTTP応答本文を受信完了した時刻、UTC |
| source_at | いいえ | 意味を確認できる提供元時刻。受信時刻で代用しない |

市場・通貨ペアは実行側のみ保持し、必要時JOINする。価格・数量はDECIMAL、JavaではBigDecimal。数値はDECIMAL(30,12)。CHECK・索引・外部キー等の定義は既存Flyway V1/V2を正とする。created_at/updated_atは目的なしに追加しない。

### 状態・保存・起動

開始時にRUNNINGを短いトランザクションで記録→外部通信（DBトランザクション外）→変換・検証→価格保存とSUCCESS更新を同一トランザクションで確定。
FAILED/SKIPPEDでは価格を作らない。外部キー・UNIQUEだけでは「SUCCESSと価格1件の対応」を保証できず、Serviceとテストで守る。

単一バックエンド前提で、DB/Flyway適用後に残ったRUNNINGをINTERRUPTEDへ更新し、それから新規収集を開始する。実停止時刻は不明なためfinished_atを埋めず、検出時刻を記録する。回収失敗なら起動を失敗させ、収集を開始しない。複数台・無停止の重複起動は別途設計が必要。
DB記録不能時はログに残す。DBが失われる代替構成では、過去のRUNNINGを回収できない点も公開条件に含める。

### Flywayの位置づけ

設計したCREATE/ALTER等を番号付きSQLとして適用し、専用履歴テーブルで適用済みを管理する。テーブルを設計してくれるツールではない。
既存V1/V2を起動時に適用・検証する。JPAの自動スキーマ変更に任せず、構造管理はFlyway、Javaとの読み書き対応はJPAという分担を採用している。

## 4. REST API【既存2本＋履歴分析1本】

合意済み：DB参照のみ、価格・数量とIDはJSON文字列、日時はUTC、API用DTO、市場・ペアを応答に含める。items配列、任意値null、データなし200、入力不正400、DB接続不能503、想定外500と共通エラーJSON（code/message）。

| エンドポイント | 用途 | 実装既定（細部はアシスタント判断） |
|---|---|---|
| GET /api/v1/quotes/latest | 市場・ペアごとの最新保存価格一覧 | exchange/symbolは任意。limitなし |
| GET /api/v1/collection-runs | 収集実行履歴 | exchange/symbol任意、limit任意・既定100・1～100 |
| GET /api/v1/quotes/history | 24時間観測と全期間スプレッド統計 | 1市場・省略時Coinbase/BTC、一覧最新2000件と上限通知 |

一般的な価格履歴GET /api/v1/quotesは提供しない。今回の合意でチャート用GET /api/v1/quotes/historyを追加した。DBの観測履歴は変更せず、同じ保存データを活用する。
latestは全体から1件でなく、対象ごとに最新1件。Phase 1は最大1件。履歴は条件を満たす全対象を合わせてlimit件。
既存2 APIの任意フィルター省略は絞り込みなし。空文字・未対応対象・不正件数は400、対応対象で該当データなしは200と空配列を実装既定とする。
latestは観測時刻、同時刻は観測IDで最新判定し、市場/ペア順で返す。実行履歴は開始時刻降順、同時刻は実行ID降順を実装既定とする。
最新価格・収集履歴・履歴分析の3参照は独立し、同一瞬間のDB状態を保証しない。収集結果がFAILEDでも、その履歴を正常に参照できればAPI応答は200。
契約のJSON例・確認項目はAPI基本設計.mdに整理した。入力検証・理由コードは参照APIの個別詳細設計とソースに記録済み。

### フロントとバックの分担

バック：外部形式の変換、検証、価格比較・計算、DB検索、件数・順序制限、DTO作成。
フロント：ラベル、色、レイアウト、読込・空・エラー状態、UTCからJSTの表示変換。表示用の丸めを業務計算へ流用しない。
価格・数量の文字列を安易にJavaScript Numberへ変換しない。時刻は同じ瞬間をUTCで伝え、画面で表示を変える。

## 8. 外部形式と共通データ・時刻【2026-11-01合意】

- 通貨ペアは各APIのbase/quoteの意味を確認して共通のBASE-QUOTEへ変換する。BTC-USDは1 BTCあたりのUSD価格。BTC-USDTと同一視しない。
- 取引所専用応答DTO → 変換・検証 → アプリ共通の価格観測データ → 保存、という境界を置く。共通データにCoinbase固有の配列構造を持ち込まない。
- observedAtは応答本文を受信完了したアプリ側の時刻で必須。JavaではInstant。JSON変換後やDB保存時の現在時刻で代用しない。
- sourceAtは意味を確認できた提供元時刻のみ。Coinbase book応答のtimeの厳密な意味は未確認のため、確認できるまでsourceAtをnullにする。外部DTOではtimeを受け取れるようにするが、受信時刻で穴埋めしない。
- JavaのInstantは小数秒9桁を保持できる。DATETIME(6)への保存境界でChronoUnit.MICROSへの切り捨てを明示する。共通データを作る段階ではDB都合で切り捨てない。
- Phase 1の経過時間表示は受信からの経過であり、市場データ自体の鮮度保証ではない。Phase 2で受信差・通信所要時間・提供元時刻の意味・配信方式を含めて比較可否を設計する。

## 9. Coinbase観測の採否【2026-11-01合意】

- auction_mode=trueはSKIPPED。オークション判定を通常の板の数値検証より先に行う。auction_mode欠落/nullはFAILED（状態不明を通常価格とみなさない、任意項目のため採用可能な応答を狭める点も説明済み）。
- bids/asksの空配列はSKIPPED。欠落/null、配列構造の不正、必要な値の欠落・型違い・数値変換不能はFAILED。
- 価格0以下・数量負数・Bid>AskはFAILED。Bid=Askは採用可能。構造と数値が妥当な上で数量0はSKIPPED。
- DECIMAL(30,12)へ値を変えずに収まらない数値はFAILED。末尾0を除くと収まる値は採用可能。精度を落として価格/数量を保存しない。
- CoinbaseBookConversionResultで採否を表現する。採用可能はACCEPTED、スキップはSKIPPED、不正はFAILED。ACCEPTEDは変換段階の結果であり、DB保存済みのSUCCESSではない。採用時のみMarketObservationを持ち、他は理由コードを持つ。


## 10. 定期実行の現行合意

回収Txのコミット後に初回即時予約し、以後は処理終了から60秒のfixed delay。Spring ThreadPoolTaskSchedulerを使用し、正常停止では最大30秒の完了猶予を与える。enabled=falseでも回収は行う。429後も通常周期とし、即時再試行・Retry-After対応は追加しない。詳細は[機能Dの設計](../03_詳細設計/Phase1_定期実行・起動時回収_詳細設計.md)を参照。
