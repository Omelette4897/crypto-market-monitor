# 主要な設計判断

現行実装の採用方式と制約を示す。採用検討中の案や将来構想を実装済みとは扱わない。ソース・テストの基準はmain `24669d6`（2026-11-14）。

## 1. 外部通信と短い保存トランザクションを分ける

- **方式**：CollectionServiceは全体Txを持たず、別BeanのCollectionPersistenceServiceを呼ぶ。RUNNING開始をcommit→HTTP取得→結果確定。SUCCESS更新と観測INSERTを同一Txで確定する。
- **理由**：外部API待機中にDB接続やTxを保持せず、結果保存の片方だけが残ることを防ぐ。
- **代替**：収集全体を`@Transactional`で囲む方式は簡潔だが、通信待ちまでTxが続き、開始履歴も終了まで確定しない。複数Beanへの分離はSpringのTxプロキシを通すためでもある。
- **制約**：各保存メソッドは非Txの呼出し元から利用する前提。自己呼出しや外側Txの追加で境界を変えない。分散Tx・再実行キューは導入しない。
- **根拠**：[CollectionService](../../backend/src/main/java/com/example/cryptomonitor/collection/service/CollectionService.java)、[保存Service](../../backend/src/main/java/com/example/cryptomonitor/collection/service/CollectionPersistenceService.java)、[実MySQLでのcommit / rollback試験](../../backend/src/test/java/com/example/cryptomonitor/collection/service/CollectionPersistenceIT.java)。

## 2. RUNNING条件付き更新で確定済み状態を守る

- **方式**：完了UPDATEのWHEREにRUNNINGを指定し、成功時は実行ID・市場の一致と更新件数1を確認する。保存障害後のFAILED記録もRUNNINGだけを対象にする。
- **理由**：DBでcommit済みでも応答を失う場合がある。後続の例外処理が無条件にFAILEDへ書き換えると、保存済み観測との整合性を壊す。
- **代替**：事前SELECTだけで状態を判断する方法より、UPDATE自体の条件で保護する。観測のUNIQUE・FKも併用するが、それだけではSUCCESSとの対応は保証できない。
- **制約**：二重確定を新しい成功として扱わない。実ネットワークでのcommit応答喪失の完全再現はしていない。モックで結果不明経路、実MySQLで条件付き更新を検証する。
- **根拠**：[CollectionRunRepository](../../backend/src/main/java/com/example/cryptomonitor/collection/repository/CollectionRunRepository.java)、[CollectionServiceTest](../../backend/src/test/java/com/example/cryptomonitor/collection/service/CollectionServiceTest.java)、[CollectionPersistenceIT](../../backend/src/test/java/com/example/cryptomonitor/collection/service/CollectionPersistenceIT.java)。

## 3. 回復commit後にSpring Schedulerへ明示登録する

- **方式**：ApplicationRunnerで残存RUNNING→INTERRUPTEDをcommitした後、専用ThreadPoolTaskSchedulerへfixed delayを登録する。終了はSmartLifecycleで予約取消→実行完了待機→超過時割込み要求の順に制御する。
- **理由**：未完了履歴を回復する前に新規収集を開始しないため。実停止時刻は不明なので、終了時刻を推測せず中断検出時刻を記録する。
- **代替**：単純な定期実行なら`@Scheduled`で足りるが、注釈による自動登録だけではRunnerの回復完了を開始条件にできない。JDK Executorの直接管理からSpring標準基盤へ委譲し、必要な開始・停止順序だけをアプリ側へ残した。
- **制約**：同一プロセス内の二重登録・並列実行を抑止する。複数プロセス間の排他はなく、更新時は旧App停止後に新Appを起動する。割込み要求は強制終了の保証ではない。
- **根拠**：[CollectionScheduler](../../backend/src/main/java/com/example/cryptomonitor/collection/scheduler/CollectionScheduler.java)、[Runner試験](../../backend/src/test/java/com/example/cryptomonitor/collection/startup/CollectionStartupRunnerTest.java)、[実Springライフサイクル試験](../../backend/src/test/java/com/example/cryptomonitor/collection/scheduler/CollectionLifecycleTest.java)、実DB終了順序はCollectionPersistenceIT。

## 4. 外部DTO・共通観測・Entityと時刻を分離する

- **方式**：Coinbase固有DTO→Mapper→MarketObservation→MarketSnapshot。価格・数量はBigDecimal / DECIMAL(30,12)、APIでは文字列。observedAtは本文受信完了時刻、保存時にマイクロ秒へ切捨て、画面はJST。
- **理由**：外部の配列形式や取引所固有表記を保存・参照側へ漏らさず、二進浮動小数による誤差や時刻の意味の混同を避ける。
- **代替**：doubleや受信JSONの直接保存は簡潔だが、価格の精度・型検証・取引所共通化が曖昧になる。提供元時刻を受信時刻で穴埋めする方法は採らない。
- **制約**：sourceAtはCoinbaseのtimeの意味を確定できるまでnull。受信からの経過時間は真の市場鮮度や約定可能性を保証しない。描画座標のみNumberへ変換する。
- **根拠**：[CoinbaseBookMapper](../../backend/src/main/java/com/example/cryptomonitor/coinbase/mapper/CoinbaseBookMapper.java)、[Mapper試験](../../backend/src/test/java/com/example/cryptomonitor/coinbase/mapper/CoinbaseBookMapperTest.java)、保存時刻・精度はCollectionPersistenceIT、表示計算は[marketCalculations](../../frontend/src/utils/marketCalculations.ts)。

## 5. 履歴一覧の上限とDB集計の母集団を分ける

- **方式**：最新2,000件の一覧と24時間全観測のSUM / COUNT / MIN / MAXをDBで検索し、平均をJavaで算出する。同一readOnly / REPEATABLE_READ Txで同じ期間・市場を読む。関連はfetch joinで取得する。
- **理由**：大量の全観測をJavaへ読み込まず、グラフ上限によって統計の対象まで狭くならないようにする。並行収集中のcommitで一覧と集計が別のDB時点にならないようにする。
- **代替**：Vueで取得済みグラフ点だけから集計すると、省略時に24時間全体の統計ではなくなる。最新価格参照にはSUCCESS条件を重ねず、保存側が状態・観測の対応を守る。
- **制約**：平均は観測単位の単純平均で、時間・数量加重ではない。2,000件は応答上限であり走査量上限ではない。現DDLに市場・観測時刻用の複合索引はなく、大量蓄積時の検索計画・索引・保持期間は要評価。
- **根拠**：[QuoteHistoryQueryService](../../backend/src/main/java/com/example/cryptomonitor/market/service/QuoteHistoryQueryService.java)、[MarketSnapshotRepository](../../backend/src/main/java/com/example/cryptomonitor/market/repository/MarketSnapshotRepository.java)、[QueryApiIT](../../backend/src/test/java/com/example/cryptomonitor/common/api/QueryApiIT.java)。

## 配信とUIの選択

VueをSpring Bootへ同梱し、1つのAppから同一オリジンで配信する。独立フロント配信やNginxを追加する方式より運用資源を減らす。Chart.jsは単一折れ線に必要な部品を直接登録し、decimal.jsで表示用の十進演算を行う。複雑な状態共有が不要なためPinia・Router・Axiosは追加していない。Railway採用・費用・単一起動の制約は[公開構成](../06_リリース・運用/公開構成・デプロイ設計.md)を参照する。
